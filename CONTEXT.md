# EquineRI Architecture Context

> Started 2026-10-03 from the design grill recorded in `docs/GrillLog.md`. This file is
> the decision log: it separates settled contracts from open questions. The design phase
> ended on 2026-10-10; the implementation plan is `docs/Plan.md`.

## 1. Project and design posture

A research rendering interface over D3D12 and Vulkan. Its purpose is research
velocity: sending work to the GPU must be trivial, while users retain roughly 90% of the
control a native API gives them. It sits above D3D12/Vulkan, but it does not hide what
researchers need in order to architect complex systems on top of it.

The yardstick is what users have already built: a D3D12 renderer driven by work graphs
with a custom GPU virtual-memory system, and the systems behind three papers built on
earlier Equine states (§3). The base layer must make that class of system buildable
without escaping to native code for the core loop.

Teaching is no longer a goal. Material built on this project adapts to it, not the
other way round.

**The base makes as few architecture decisions for the user as possible.** Frame
structure, lifetime policy, synchronization strategy, and the like belong to the user.
Opinionated behavior ships as helpers layered on top of the base, and a user must always
be able to write their own replacement for any helper (P15). Because the base has no
concept of frames in flight or double/triple buffering, it is a rendering *interface*,
not an engine: hence the name EquineRI (P13).

**No architecture choice that can affect performance is made without careful joint
evaluation** (P18). A proposal that might cost performance becomes a measurement first.

## 2. Settled decisions

Code fragments in rows written before P81 use method syntax (`cmd.discard(...)`,

| P27 | Native commands mid-list use an in/out map. On entry (`beginNative`), Equine gives the native command buffer and each texture's native resting layout. | P28 | Backend selection: one backend per compiled library, with direct calls and no runtime dispatch. | P29 | The base consumes bytecode only: SPIR-V for Vulkan, DXIL for D3D12. Shader compilation is not a base concern. A helper for dynamic (runtime) DXC compilation is provided. | Round 8 |
| P30 | Shader-side bindless access is whatever the shader uses: the global heap (`ResourceDescriptorHeap[]`), declared unbounded arrays, or a mix. Equine follows reflection and imposes no style. A style the toolchain or driver cannot support on a backend fails per P11. Checking DXC/driver support for the global heap on Vulkan is an implementation task. | Round 9 |
| P31 | Memory: RI is level 2. The user allocates memory blocks and places buffers and textures in them at offsets, which permits custom allocators and aliasing. Automatic allocation (level 1, `createBuffer` without a block) is a helper on top. Whether that helper uses VMA/D3D12MA or an in-house allocator is decided under P17. | Round 10 |
| P32 | Memory kinds: a short list. GPU, Upload (CPU→GPU), Readback (GPU→CPU), and GPU + CPU write (ReBAR: Vulkan device-local + host-visible, D3D12 `GPU_UPLOAD`). Equine maps each kind per backend. The full native list is reachable through native access (P22). Availability and size of GPU + CPU write are a capability query (P11) and differ per backend: on Vulkan, systems without resizable BAR expose only a small (~256 MB) device-local + host-visible window; on D3D12, `GPU_UPLOAD` is all-or-nothing, present only when all of VRAM is CPU-visible (ReBAR enabled), with a recent Agility SDK and Windows 11 build, and absent otherwise. | Round 11 |
| P33 | Mapping: GPU memory is never mapped. Upload, Readback, and GPU + CPU write blocks are mapped once at allocation and stay mapped for their lifetime. Equine selects coherent memory so no flush/invalidate calls are needed (to confirm with `vulkaninfo` that coherent readback types exist on the floor drivers). Upload and GPU + CPU write memory is write-only from the CPU in practice: CPU reads are very slow. | Round 11 |
| P34 | Recording is immediate: each RI command call writes the native command at once. Command lists are submitted **once**, then reset (resubmission dropped in v1, P63). Anything deferred is a helper on top. Multithreaded recording is **not** in v1 (P56). | Round 12 |
| P35 | Frame graph: if one is provided, it is a helper on top of RI, driven by **declarations** of what each pass reads and writes, never by inspecting commands. (Bindless makes command inspection impossible: commands do not reveal which textures are read.) RI must therefore provide: (1) stage→stage barriers, (2) placed memory (P31), (3) a **discard** command that resets a texture taking over aliased memory, and (4) multiple queues if the graph schedules async compute (Y2). Pass bodies may use any RI or native command. **User dislikes the pass abstraction and capturing lambdas**: the helper's authoring shape is to be redesigned at implementation time. The sketch in the grill log is not a commitment. | Round 12 |
| P36 | Barriers in RI are explicit (user-issued), coarse stage→stage by default. **Inference rule (applies to all of RI):** RI prefers not to infer. It infers only what is **evident** (knowable for certain without tracking past commands) or what **greatly simplifies the API**, and it always keeps an explicit override. Barriers between user work are not evident under bindless (commands do not reveal which resources shaders touch), so automatic barriers exist only in helpers (for example the frame graph, P35). Follows from P15, P34, and the A' direction of L1; if A' fails measurement, this decision is revisited with L1. | Round 12; softened in the Inference review 2026-10-10 (`docs/Review-Inference-2026-10-10.md`) |
| P37 | v1 has only the graphics (direct) queue. Compute and copy queues come later. Timeline points (P20) are per queue, so they extend to multiple queues without redesign. **Passing textures between queues is still open** (review C4): the D3D12 resting layout `DIRECT_QUEUE_COMMON` is graphics-queue only, and Vulkan queue-family ownership transfers name the image. Options for later: a resting layout valid on all queues (or `CONCURRENT` sharing), cost to be measured; or one RI "hand texture to queue X" command, the only place textures would be named. Mostly backend-internal (P16); only the hand-off command adds API. | Round 13, amended review C4 |
| P38 | Pipelines take their complete state up front: shaders, fixed-function state, and render target formats (color, depth, sample count). The native PSO is compiled at creation, at a moment the user chooses; RI never compiles pipelines implicitly during recording. Lazily completing formats or variants at first use (V2's model) is an optional helper. | Round 14 |
| P39 | Geometry input: no classic vertex buffers or input layouts. Vertices reach shaders by vertex pulling (bindless buffers indexed by `SV_VertexID`) or through task/mesh shaders. Index buffers are supported for indexed draws. Classic vertex input may be retrofitted if it becomes a problem. | Round 15 |
| P40 | Rendering sections: `beginRendering` / `endRendering` (dynamic rendering; no render-pass objects). Each attachment, including every MRT color target and depth, takes its own load operation (`eLoad` / `eClear` / `eDontCare`, plus a clear value) and store operation (`eStore` / `eDontCare`). Defaults are `eLoad` / `eStore`. | Round 16 |
| P41 | **Control + convenience pattern.** For any mechanism, RI exposes the explicit, controllable form, and the automatic form is a helper built only on RI's public surface. Instances: memory (P31), lifetime (P20), barriers (P36), pipelines (P38), descriptors (P42). Apply it by default to new topics. | Round 17 |
| P42 | Descriptors: the user writes descriptors (resource views, samplers) into heap slots they choose. Several views of one resource may occupy different slots. Automatic slot assignment on resource creation (`bindlessIndex()`) is a helper (P41). | Round 17 |
| P43 | Windows and swapchains: RI creates no windows. It takes a native window handle (`HWND`, X11 window, Wayland surface) and creates a swapchain. The user controls present mode and resize recreation. `imageCount` is optional (RI picks a default for the present mode). `acquire()` returns the image to draw into, with no index exposed, and blocks if none is free. Acquire/present synchronisation is internal. Swapchain image cycling is **not** frames in flight: CPU/GPU overlap and duplicated per-frame data remain opt-in helpers on timeline points (P20, P13). A GLFW-based window helper lives outside RI (P17). The present model is settled by P63. | Round 18 |
| P44 | Root data size and layout are whatever the shader declares; RI chooses no budget. If the declaration is not representable on the backend/device (for example it exceeds the push/root constant limit), pipeline creation fails with a readable error (P11). | Round 19 |
| P45 | Root data is marked in the shader by the helper macro `EQ_ROOT_DATA(Type, name)` (`equine/root.hlsli`): on Vulkan it expands to `[[vk::push_constant]] ConstantBuffer<Type> name`; on D3D12 to `ConstantBuffer<Type> name : register(b0, space999)`, a **reserved register space** that survives compilation (also with stripped reflection). There is **no `[RootSignature]`, no size, and nothing per entry point**: RI builds the D3D12 root signature itself (P67): heap-indexing flags, root constants at the marked buffer with its size, and parameters for other declared resources. Space 999 has no runtime cost (spaces are binding-model labels); the user cannot use it for other resources, and RI reports a readable error if something else is declared there. Other constant buffers are ordinary. A missing or ambiguous marking (several root buffers) is a readable error. Hand-written native markings remain possible: a shader carrying its own `[RootSignature]` is used as-is (P23 "a/d"). Tested with DXC 1.8.2502. | Round 19; replaced in the Inference review 2026-10-10 (`docs/Review-Inference-2026-10-10.md`) |
| P46 | Samplers live in the sampler heap, written into user-chosen slots (P42) and picked by index in the shader. No static samplers for now; they can be added later (they are expressible in HLSL only on D3D12). | Round 20 |
| P47 | Transfers: RI provides recorded copy commands (buffer→buffer, buffer→texture, texture→buffer, texture→texture) and a copy-layout query reporting the exact staging layout (row pitch, total size, alignment) per texture subresource, so users never learn per-backend alignment rules. Upload = write to Upload memory + copy + submit; readback = copy to Readback memory + wait on the timeline point + read. One-call `upload`/`readback` with staging management is a helper (P41). | Round 21 |
| P48 | Indirect execution. Level 1 (always available): GPU-written arguments and draw counts for indexed draws, mesh-task draws, and dispatches. Level 2 (behind a capability query, P11): the GPU also changes root data between draws, via D3D12 `ExecuteIndirect` or Vulkan `VK_EXT_device_generated_commands` (NVIDIA; RADV since Mesa 24.3; AMD Windows unconfirmed). On D3D12 the Level-2 query always succeeds. Note: Level 1 has no portable per-draw identifier. Vulkan has `DrawIndex`, but D3D12 has no draw-ID builtin, so per-draw identification on D3D12 uses a Level-2 root constant or an SM 6.8 `SV_StartInstanceLocation` / first-instance trick. | Round 22 |
| P49 | Acceleration structures (inline RT): RI provides a size query (structure + scratch sizes), user-placed storage (P31), and recorded `buildBLAS` / `buildTLAS` / `update` (refit) / `compact` commands. TLAS instances are a user-written buffer in the shared 64-byte instance format (identical on D3D12 and Vulkan). TLASes are bound through descriptor slots (P42). One-call building with memory/scratch/compaction management is a helper (P41). | Round 23 |
| P50 | Work graphs: D3D12 only for now. RI provides up-front program creation from node shaders (as P38), a backing-memory size query with user-placed backing memory (P31), and a recorded `dispatchGraph(program, inputRecords)`. On Vulkan, creation fails with a clear error (P11). `VK_AMDX_shader_enqueue` (AMD-only, provisional) may be revisited if it is finalized. Automatic backing-memory management is a helper (P41). **Hardware:** work graphs need Ampere+ / RDNA3+ even on D3D12 (Agility SDK 1.613+, `D3D12_OPTIONS21::WorkGraphsTier`), so on the P3 floor (Turing, RDNA2) the capability check fails on both backends, and the work-graph reference workload needs above-floor GPUs. | Round 24 |
| P51 | Queries: user-created query pools (timestamp, pipeline statistics, occlusion) with recorded `writeTimestamp`, `beginQuery` / `endQuery`, and `resolveQueries` into a user buffer (typically Readback memory, read after the timeline point), plus a device query for timestamp frequency. A named-scope GPU profiler is a helper (P41). Details in P71. | Round 25 |
| P52 | MSAA resolve, both forms: (1) a per-attachment `resolveTo` target performed at `endRendering`, and (2) a recorded `cmd.resolve(src, dst)` command. | Round 26 |
| P53 | Debugging. (1) Object names and command markers are always on (`VK_EXT_debug_utils`; D3D12 `SetName` / PIX events). (2) GPU crash diagnostics (D3D12 DRED; Vulkan `VK_EXT_device_fault`) are enabled by the validation flag (P21). (3) Shader `printf`: Vulkan now, via DXC + validation-layer debug printf under the validation flag; a D3D12 implementation (buffer-backed) later, as a helper. (4) Bindless index checking via Vulkan GPU-AV / D3D12 GPU-based validation, under the validation flag. | Round 27 |
| P54 | Scope of "the shader is the source of truth": the binding layout (P23), root data size and shape (P44, P45), and bindless access style (P30) come from the shader. Pipeline settings and formats come from C++ (P38). The C++ mirror of root data is written by the user and checked against reflection under validation (P24). A shared `.hlsli` header compiled by both HLSL and C++ (with HLSL-type shims) is a helper (P41). Correction (review 2026-10-04): validation can reliably check the root data *size*, not member offsets, unless the user or the shared-header helper supplies member offsets. DXIL and SPIR-V can also lay out the same HLSL differently (DX root-constant/cbuffer packing vs DXC SPIR-V std430-style push constants; e.g. `float w[4]` has a 16-byte stride under DX packing and 4 bytes under std430), so one C++ mirror fits both backends only if shaders are compiled with a fixed rule such as DXC `-fvk-use-dx-layout`. The compile helper (P29) and the shared-header helper document that flag. | Round 28 |
| P55 | Agility SDK: CMake downloads a pinned NuGet version at configure time, verified by SHA-256 (`cmake/EquineAgilitySDK.cmake`, currently 1.619.6, the latest stable on 2026-10-04). Each D3D12 executable exports `D3D12SDKVersion` / `D3D12SDKPath` through the `EQUINE_D3D12_AGILITY_SDK_EXPORTS()` macro (`backends/d3d12/D3D12AgilityExports.hpp`), and `equine_deploy_agility_sdk(<target>)` copies the runtime to `<exe dir>/D3D12/`. Exports in a DLL are ignored, so with the P28 wrapper, the wrapper executable carries the exports (in its Windows build) and is the deploy target. A `static_assert` in the export header guards against the Windows SDK `d3d12.h` shadowing the Agility one. | Round 29 |
| P56 | v1 records commands from one thread only (research workloads have few draw calls); this supersedes the Round 3 "multithreaded recording: yes". RI objects are not thread-safe in v1. Following P41: command lists (with their native pool/allocator) are user-owned and may be reset/reused only after their timeline point (P20) has completed; automatic recycling is a helper. Multithreaded recording may be added later. | Review round B1 |
| P57 | Error model: **undecided; keep it easy to change.** Every failure site reports through one central channel with a category (programmer error, unsupported feature, device lost, out of memory, swapchain needs recreation). The policy for each category (abort with message, throw, return a status, or a user callback) lives in one place, so changing the model later touches one file, not every call site. Proposals on record (not decided): abort for programmer errors/unsupported/device lost; status returns for swapchain recreation, allocation failure, and pipeline creation failure (hot reload). Signature changes (e.g. adding status returns later) are acceptable: the user is the only user until the API is settled and will iterate on it (X1, 2026-10-10). | Review round B2 |
| P58 | Resource creation: textures (and buffers) take **explicit usage flags** (sampled, storage, render target, depth-stencil, copy source/destination, …). These flags also drive the backend-internal resting layout (L1) without exposing layouts. A helper picks usages automatically (P41). Consequences, applied by default (P41/P31/P11): (1) a memory-requirements query per resource description (size, alignment, compatible memory kinds — D3D12 `GetResourceAllocationInfo` + heap rules, Vulkan `memoryTypeBits`), needed to place resources in user memory; (2) a format/usage support query, with unsupported combinations failing clearly (e.g. D24S8 on AMD Vulkan). Still open: format reinterpretation (typeless/mutable formats) and subresource-range views (part of R10). | Review round B3 |
| P59 | Descriptor heaps: the user creates the resource heap and the sampler heap with sizes they choose, within device limits that RI reports. A default-heap helper picks sizes automatically (P41). Descriptor writes take effect immediately; the user must not overwrite a slot that in-flight GPU work may read, and waits on its timeline point first (same rule as destruction, P20). The Vulkan mechanism behind it (update-after-bind descriptor indexing, descriptor buffer, or descriptor heap extension) is a backend implementation choice. | Review round B4 |
| P60 | Device creation. (1) RI lists the GPUs (name, vendor, memory) and the user picks one; picking the dedicated GPU automatically is a helper. (2) No RI feature list: D3D12 has no enable step, so the Vulkan backend enables **everything the GPU supports** at creation to behave the same, except features that cost performance merely by being on (robustness), which stay off unless requested. (3) Device creation accepts native additions: extra Vulkan extensions/feature structures (which can also override RI's choices) and a D3D12 pre-device hook (e.g. experimental features), so creation-time features never block the user (P22). (4) Capability queries are wrapped only for features RI's own commands use (mesh, ray query/AS, work graphs, indirect level 2, …); anything else is queried natively. Rationale: wrapping every feature behind a cross-API boundary is a maintenance burden that recreates the papers' missing-feature failure mode. | Review round B5 |
| P61 | GPU addresses: RI provides host-side `gpuAddress()` for buffers and acceleration structures (64-bit). It is needed for TLAS instances (P49), work-graph GPU inputs (P50), and user tables such as virtual-memory systems. On Vulkan, all memory and buffers are created addressable (`VK_MEMORY_ALLOCATE_DEVICE_ADDRESS_BIT`, `SHADER_DEVICE_ADDRESS` usage), matching D3D12 where every buffer has an address. How shaders use addresses stays the user's choice (P7). | Review round B6 |
| P62 | Work-graph details (extends P50). `dispatchGraph` supports all four D3D12 input modes: CPU records or GPU records (by address, P61), each for a single entry node or multiple. **Backing-memory initialization is inferred** (P36 rule): each program stores the backing memory it was last dispatched with, and RI sets D3D12's `INITIALIZE` flag on the first dispatch and whenever the backing memory changes; an optional "force initialize" flag resets the scratch state deliberately. Root data of library (work-graph) shaders: whether RI can read them like other shaders (P45, P67) is checked at implementation; otherwise the native `GlobalRootSignature` subobject is used. Per-node local root arguments are a user-written buffer (address + stride), like TLAS instances. | Review round B7; amended in the Inference review 2026-10-10 (`docs/Review-Inference-2026-10-10.md`) |
| P63 | Submit and present follow the D3D12 swapchain model on both backends. (1) No command-list resubmission in v1 (amends P34): every list is recorded, submitted once, then reset; research workloads re-record each frame, so replaying saves little CPU time and would add rules (stale swapchain images, lifetimes across replays). It may return later. (2) Per frame, the user asks the swapchain for the **current screen texture** (the P43 `acquire()`), draws into it directly like any texture, submits, then calls `present()`. No copy, no emulated screen texture. (3) On D3D12 this is the native model (back-buffer index, queue ordering, `Present`). On Vulkan, RI hides the acquire and present semaphores: the GPU work that uses the current texture waits on the acquire, and `present()` waits for the submitted work, does the base-owned transition to `PRESENT_SRC` (R16), and presents. The exact wiring of these internal waits is an implementation detail, checked with group C (sync scope of RI-emitted transitions). How out-of-date/suboptimal is reported stays with X1. | Review round B8 |
| P64 | Swapchain format and color space (extends P43). (1) RI queries the (format, color space) pairs a window supports (sRGB, HDR10/PQ, scRGB, …); the user picks one at swapchain creation. (2) The chosen format is readable, so pipelines can target it (P38). (3) A helper picks a default (BGRA8 + sRGB). (4) Tearing is a present mode, not a separate flag. (5) Compute (storage) writes to the screen texture are a capability, queried per window and per format: D3D12 flip-model back buffers never allow them, and on Vulkan it depends on the surface and format. **This must be stated clearly in the API and docs.** Note: a user who wants compute-to-screen on every backend renders into a normal texture and copies it to the screen; this "emulated screen" is a good candidate for a helper (the P18 cost of the copy is then the user's explicit choice), and it is the one strong reason found so far to revisit the emulated screen texture rejected in P63. | Review round B9 |
| P65 | Clears outside rendering sections are RI commands, not helpers: `clearBuffer(buffer, value)` and `clearTexture(texture, value)`, with no slot argument. Vulkan uses the native commands (`vkCmdFillBuffer`, `vkCmdClearColorImage`). The D3D12 backend implements them with its own internal compute shaders (what most engines do) instead of `ClearUnorderedAccessView*`, which would need the user's heap slot plus a CPU descriptor. Consequences for the D3D12 backend: (1) buffers bind by GPU address (root UAV), no descriptor needed; (2) textures need a shader-visible descriptor: the backend switches to its **own small shader-visible heap** for the clear and switches back to the user heap afterwards (B10a), so no user slot is reserved. Known cost: a heap switch may stall the GPU on some hardware (P18). **Reassess** if this stall shows up in measurements, or if another feature also needs RI-owned slots; the alternative is a few RI-reserved slots at the end of the user heap; (3) the backend restores the user's pipeline and root data after the clear, which immediate recording (P34) makes possible since RI knows what was bound; (4) one shader per value type (float/uint/int) and texture dimension. | Review round B10 |
| P66 | No memory budget query and no residency control in RI: irrelevant to the research use case. Users who need them go native (P22): D3D12 `QueryVideoMemoryInfo` on the adapter, Vulkan `VK_EXT_memory_budget` (already enabled by P60); residency via `MakeResident`/`Evict` or `VK_EXT_pageable_device_local_memory`. Docs only list which native memory pool each RI memory kind (P32) uses. Added if a user requests it. | Review round B11 |
| P67 | Shader reflection sources (completes P23/P24/P45). D3D12: RI's **own small DXIL reader** reads the heap-indexing flags (`SFI0` part), the bindings (`PSV0` part), and constant-buffer sizes (the DXIL part's `dx.resources` metadata, present even with `-Qstrip_reflect`), and builds the root signature; prior art: dxil-spirv's minimal LLVM bitcode parser (MIT). DXIL is frozen on LLVM 3.7 bitcode. **No `dxcompiler.dll` at runtime** in release: users must not need HLSL compilation available at runtime. Vulkan: **SPIRV-Reflect** reads push-constant size and descriptor sets/bindings (P17 dependency, accepted "for now"; an in-house reader remains possible). Field-level validation of root data (P24) may load `dxcompiler.dll` at runtime on D3D12 **only in validation builds** (P21). | Review round B12; amended in the Inference review 2026-10-10 (`docs/Review-Inference-2026-10-10.md`) |
| P68 | Sync scope of RI's own layout transitions (A', L1; applies on D3D12 and on Vulkan without `VK_KHR_unified_image_layouts`). RI knows its own operation, so the half of each transition touching it is **exact** (P36 inference rule) and the other half stays **full**: a transition **into** an RI operation (rendering, copy, clear, resolve, present) waits for all earlier work and blocks exactly that operation; a transition **back** to resting after it (e.g. at `endRendering`) waits exactly for that operation and blocks all later work. Written immediately, with no held-back or merged user barriers, so no hidden state (P34). Its cost is part of the L1 measurement (LayoutEvaluation item 2); merging the user's adjacent barrier is the fallback if the cost shows up. | Review round C1; amended in the Inference review 2026-10-10 (`docs/Review-Inference-2026-10-10.md`) |
| P69 | Discard (defines P35 (3)). `cmd.discard(texture)` is **required** before the first use of any texture (attachment or not) whose memory previously held another resource. It resets contents and hidden compression metadata: Vulkan `UNDEFINED` → resting layout; D3D12 enhanced barrier from `LAYOUT_UNDEFINED` with the `DISCARD` flag → resting layout (which also satisfies D3D12's aliased RT/DS initialization rule). Load operations (`eClear`/`eDontCare`, P40) do **not** count as a discard. It is a full-scope barrier (P68). Buffers need no discard. With validation (P21), RI tracks memory placements and reports a texture used without discard after taking over memory; release builds track nothing. A newly created texture's initial reset is done by RI itself (R16). Subresource-range discard waits on R10. | Review round C2 |
| P70 | Native-section contract (extends P27). (1) `endNative` restores **all** state RI relies on: its implicit state (D3D12 descriptor heaps / Vulkan bindless set, and the matching root signature or pipeline layout) and the user's last pipeline and root data bound through RI, reusing the restore mechanism of the D3D12 clear (P65). After the section, state equals the state before `beginNative`, except the textures listed in the out map. Any internal bind cache is invalidated. (2) Native sections are allowed inside `beginRendering`/`endRendering`; there, native code must not end rendering or change attachments, and no out map is allowed (layouts cannot change while rendering). | Review round C3 |
| P71 | Query details (extends P51). (1) Reset: the pool is reset on the CPU at creation (host reset, Vulkan 1.2 `vkResetQueryPool`). After reading results (after the timeline point), the user calls `pool.reset(first, count)`, a CPU call with no GPU cost, a no-op on D3D12. The recorded `resetQueries(pool, first, count)` remains for resets in the middle of a command list (not inside a rendering section). GPU auto-reset after resolve was rejected (GPU cost). A "read results" helper may read and reset. Resolve (D3D12 `ResolveQueryData`, Vulkan `vkCmdCopyQueryPoolResults` with 64-bit + wait flags) never empties queries. (2) Results: timestamps and occlusion are one 64-bit value per query on both backends. Pipeline-statistics layouts differ (D3D12 fixed 11/13-counter struct; Vulkan only enabled counters, in bit order), so RI provides a **result-layout query** giving each counter's offset (like the P47 copy-layout query); no conversion. A struct-producing helper is optional (P41). (3) Timestamp frequency stays a device query while v1 has one queue; it gains a queue parameter when queues are added (P37), since D3D12 frequency is per queue. | Review round C5; amended in the Inference review 2026-10-10 (`docs/Review-Inference-2026-10-10.md`) |
| P72 | Fine-grained synchronization (settles Y4, P10). RI has **no resource-naming barrier**. "Fine-grained" means (1) precise source/destination stages and accesses in the coarse barrier (P36), and (2) native sections (P27) for anything finer. Rationale: on desktop drivers a barrier that changes no layout costs about the same whether it names one resource or none, and under A' user barriers never change layouts; naming resources is what P26 rejected. Revisit only if a measurement shows a gain (P18). | Open item Y4 |
| P73 | Texture views (R10, part 1). "Part of a texture" (mip range, layer range, aspect) is named by **view objects** the user creates explicitly, once (`device.createView(texture, {mip, layers, aspect, …})`), like Vulkan `VkImageView`. Attachments (P40), discard (P69), resolve (P52), and descriptor writes (P42) take views. RI keeps no hidden view cache and creates no native view behind the user's back. Convenience: every texture comes with a ready-made **whole-texture view**. Copies keep their per-subresource form (P47). | Open item R10 |
| P74 | Format reinterpretation (R10, part 2). Texture creation takes an optional list of **extra view formats** (Vulkan `MUTABLE_FORMAT` + format list; D3D12 castable formats). Empty by default: views use the texture's own format only. An exact list lets drivers keep compression. Creating a view with an unlisted format is a readable error; validation (P21) also checks compatibility (same bits per texel). Same pattern as the usage flags (P58): stated at creation, and a helper may fill it in (P41). | Open item R10 |
| P75 | Read-only depth (R10, part 3). The `beginRendering` depth attachment takes `depthReadOnly` and `stencilReadOnly` flags (default off). When set, RI's around-rendering transition (A') targets the read-only depth layout on D3D12 and on Vulkan without unified layouts, which allows sampling the same texture during the section (soft particles, decals). Validation (P21) reports a depth-writing pipeline used inside such a section. On Vulkan with unified layouts the flags have no native effect but are written for portability. | Open item R10 |
| P76 | Resolve modes (R10, part 4; extends P52). `resolveTo` and `cmd.resolve` take a mode: `average`, `min`, `max`, `sampleZero`. A capability query (P11) reports the modes supported for depth and for stencil. An unsupported mode is a readable error. **No emulation**: D3D12 has no `sampleZero` and RI does not emulate it (an internal draw writing `SV_Depth` was considered and rejected). `min`/`max` are the portable depth modes on desktop hardware; resolving in a user shader always works. Internal emulation is decided case by case (yes for clears, P65; no here); no general rule. | Open item R10 |
| P77 | Native-to-RI import (settles I1; makes P22 two-way). (1) `device.importTexture(native, desc)`, `importBuffer`, `importMemory`, `importPipeline` wrap natively created objects as RI objects. The user supplies a short description (format, size, usage), since Vulkan cannot report image creation info. **RI does not own imported objects**: destroying the RI object only forgets it; the user destroys the native object. An imported texture must be in RI's resting layout before RI first uses it; RI reports that native layout (as `beginNative` does, P27). (2) A raw descriptor write puts a **native** descriptor (Vulkan `VkDescriptorImageInfo`/`VkDescriptorBufferInfo`, D3D12 CPU handle) into a user heap slot, for view types RI does not model. | Open item I1 |
| P78 | Vulkan without `VK_KHR_unified_image_layouts` (RDNA2): the backend implements **both** A' modes, G (everything rests in `GENERAL`, no switches) and T (D3D12-style resting layout with around-operation switches, P68). The measurement (LayoutEvaluation items 2–3) decides the faster one; the backend selects it automatically at device creation from GPU and driver, and a device-creation option can force either mode for testing. Backend-internal: user code is identical in both modes (P16). | Open item L1 |
| P79 | L1 decision rule, fixed before measuring. Baseline: hand-written optimal per-texture layout transitions (candidate B, rejected as an API but used as the speed reference). A' is accepted if, on **every** tested GPU (Turing, RDNA2, and newer): (1) a realistic frame is at most **2%** slower than the baseline, and (2) no single pass is more than **10%** slower, unless the absolute difference is under **0.05 ms** (noise floor). Otherwise, the fallbacks in `docs/LayoutEvaluation.md` apply (other mode per GPU, P78; accept the cost; opt-in per-texture mode; reopen L1 together). | Open item L1 |
| P80 | EquineRI is designed for itself. The layer the user will build on top of it (EquineEngine) is **not** RI's concern: it must not shape or leak into RI's API, and RI makes no provision for it. RI's API style is not constrained by the user: the assistant proposes and the user picks (`docs/RIApiProposal.md`). U1 (the hello-world) is dropped. | 2026-10-10; amended the same day |
| P81 | RI object model: **thin value objects** (style B, `docs/RIApiProposal.md`). An RI object (`RI::Buffer`, `RI::Texture`, …) is a small copyable struct holding the native handle(s) and a few cached facts (size, GPU address); it owns nothing, like a `VkBuffer`. No lookup table, no RAII. Facts are fields (`buf.gpuAddress`, P82); native handles are reached through the native header (P84); destruction is explicit and immediate on the device (`device.destroy(buf)`, P20). Use after destroy is detected only in validation builds (P21). | RI API proposals, Q1 |
| P82 | Code style of RI (user preference: no OOP). (1) RI types are **plain data structs with public fields**; facts about an object are fields (`buf.size`, `buf.gpuAddress`), not methods. (2) Operations are **free functions** taking the struct (`RI::createBuffer(device, memory, offset, desc)`), so RI functions, helpers (P41), and the user's own helpers share one style. Methods only where they clearly make sense (none identified yet). (3) Hidden state uses no `private`/`protected`: it lives in an unnamed struct field named `internal` (EquineEngineV2 convention), so the user sees clearly that nothing there is guaranteed. (4) The `Device` struct exists because its data lives and dies together (native device, function tables, RI's internal state); a hidden global device was rejected. Amends P81's examples (`buf.gpuAddress()` → `buf.gpuAddress`). | RI API proposals, Q2 |
| P83 | Backend structure (refines P28). Each backend defines its own structs and functions in its own namespace (`RI::Vk::`, `RI::D3D12::`); nothing is shared between backends, so adding a backend changes no existing struct. `RI::` is an alias to one backend, chosen by the build (`EQUINE_BACKEND_VULKAN` / `EQUINE_BACKEND_D3D12` macros). Both backends can coexist in one program (P28 wrapper, tests) with user code compiled once per backend. Consistency: the same free-function signatures and the same portable field names in every backend, enforced by a conformance source file compiled against each backend. | RI API proposals, Q2 |
| P84 | Native access is gated (refines P22, P27, P60, P77). Portable RI headers contain no native types; native handles are kept in `internal`. Native access requires (1) including the backend's native header (`<RI/Vk/Native.hpp>`, `<RI/D3D12/Native.hpp>`) and (2) naming the backend explicitly (`RI::Vk::native(device)` → a plain struct of native handles). The `RI::` alias does not bring native functions in. Everything native lives there: handle structs, import (P77), `beginNative`/`endNative` (P27), device-creation additions (P60). Per-backend native code is written in `#if EQUINE_BACKEND_*` blocks; native code for the wrong backend fails to compile. | RI API proposals, Q2 |
| P85 | Recording functions carry a **`cmd` prefix**, like Vulkan's `vkCmd*`: `RI::cmdDispatch(cmd, x, y, z)`, `RI::cmdBeginRendering(cmd, …)`, `RI::Vk::cmdBeginNative(cmd)`. Commands read as commands at a glance, native commands keep the explicit backend name (P84), and user helpers follow the same shape (`cmdBlur(cmd, …)`). Methods on the command list were rejected: they cannot be added by the native header, so they would either mix styles or drop the backend name. (A user layer on top may wrap them into objects with methods; RI does not plan for it, P80.) | RI API proposals, Q2 |
| P86 | Descriptions are plain structs filled with C++20 designated initializers, with sensible defaults (as in V2); no builders, no long argument lists. Naming (as V2 and vulkan.hpp): `RI::` namespace, `camelCase` functions, `PascalCase` types, enumerators prefixed with `e` (`RI::MemoryKind::eUpload`), flags combined with `\|`. | RI API proposals, Q2 |
| P87 | Descriptor kinds are named by access, with "View": `RI::ReadView` (D3D12 SRV; Vulkan sampled image, read-only storage buffer, or acceleration structure), `RI::ReadWriteView` (UAV; storage image or storage buffer), `RI::ConstantBufferView` (CBV, D3D12's own full name; uniform buffer); samplers are written as the `RI::Sampler` itself. A field names the target: `.texture` (a P73 texture view), `.buffer` (with range, and stride or format for typed buffers), `.accelerationStructure`. Optional free helpers `RI::srv(x)`, `RI::uav(x)`, `RI::cbv(x)` build them. The batching form of the write function stays open (D1). | RI API proposals |
| P88 | Where RI's own checks live (refines P21). (1) **Shared check functions** in a common `validation/` folder (plain free functions, written once for all backends); each backend function calls them through one `EQ_VALIDATE(...)` line that compiles to nothing in release; tracking state (destroyed objects, memory placements, in-flight slots, query resolves) lives in `internal` only in validation builds. (2) **Scope:** RI checks only what native layers and GPU-AV (P53) cannot see: RI's own rules (discard after aliasing P69, native out map P27, root-data marking and size P45, read-only depth P75, view formats P74, slot reuse P59, command-list reuse P56, …). A forwarding validation backend was considered and not chosen (wrapper structs, unwrapping for native access). | RI API proposals |

## 3. Reference workloads

These are capability targets, not port targets:

- three published papers built on various EquineEngine states. All three use mesh and
  compute shaders and use Equine purely as a graphics API. Their main cost was hitting
  features Equine had not implemented and implementing them mid-project. A native API
  would have caused no such problem, except that the co-authors are not fluent in one;
- a D3D12-only system combining work graphs with a custom GPU virtual-memory system.

## 4. Carried over from EquineEngineV2

Taken as-is into the scaffold, open to revision:

- `.clang-format`, `.clang-tidy`, `.clangd`;
- the compiler-runtime policy: exceptions on, ASan + UBSan on by default, a `bench`
  preset without sanitizers, clang-tidy in every build;
- `types.hpp` (integer aliases only) and RavenLib's `bitmask.hpp` (flag operators, P86). Removed on 2026-10-10 as stale for v1: `handles.hpp` (handles rejected by P81), `utils/macros.hpp`, RavenLib's slotmap, and glm (RI's API needs no math library; the user's choice, P15);
- the dependency-free self-registering test harness with one CTest entry per case;
- `FindDXC.cmake` and the single-DXC-for-both-targets rule.

Explicitly **not** carried over as decisions, though available as reference: the
record → compile → resident → execute lifecycle, command patching, the graph compiler,
reflection-driven binding tables, and the print-and-return-invalid stub convention
(it conflicts with P11; its macros were removed in the review cleanup).

## 5. Open questions

Settled during implementation (`docs/Plan.md`).

- **L1. Hiding image layouts under bindless (P16). Blocking; requires joint evaluation
  (P18).** Direction A': one resting layout; RI transitions only around its own
  operations, with exact/full halves (P68). B is rejected (P26). RDNA2 Vulkan runs modes G
  and T, chosen by measurement (P78). Decision rule fixed (P79). What remains is the
  measurement (Milestone 3, `docs/LayoutEvaluation.md`). If A' fails as a whole, L1 is
  reopened with the user (P16 and P36 depend on it).
- **D1. Descriptor-write batching.** Provisional form: one `RI::writeDescriptors(device,
  heap, writes)` taking a list of `{slot, descriptor}` (P87 kinds), a single write being a
  list of one; one native call on Vulkan, a loop on D3D12. Kept open until the Vulkan
  descriptor mechanism is chosen (descriptor sets with update-after-bind vs descriptor
  buffer / descriptor heap extensions, P59), in Milestone 2.
- **X1. Error policy per category (P57).** Deliberately open: the user settles it by using
  the API; signature churn is acceptable until then.
- Implementation choice: the Vulkan loader (Vulkan::Vulkan vs volk).
