### R01. The Vulkan resting layout on RDNA2 (SHADER_READ_ONLY) cannot take storage writes, so usage leaks after all

- Items: L1, P16, docs/LayoutEvaluation.md  ·  Kind: factual-error  ·  Reviewer severity: high
- Finding: LayoutEvaluation's coverage section says that on RDNA2 without unified layouts, Vulkan does 'the same around-pass transitions as D3D12, with `SHADER_READ_ONLY`/`GENERAL` as the resting layout.' VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL does not allow storage-image writes. Bindless compute writes therefore need GENERAL, so the resting layout depends on how the texture is used. That is the exact leak the doc says it avoided ('A' does not leak a usage decision on D3D12'). The claim only holds for D3D12, where DIRECT_QUEUE_COMMON covers SRV+UAV.
- Suggestion: Fix the resting layout for non-unified Vulkan at GENERAL (one layout, measured), or say openly that a usage flag at texture creation is needed. Add this to measurement item 2/3.
- Verifier: Downgrade to low severity, kind "imprecision" rather than "factual-error". The fix is to state in LayoutEvaluation's coverage section that on non-unified Vulkan, the resting layout is chosen per texture from the usage bits that texture creation already requires. Storage-capable textures rest in GENERAL and sampled-only textures rest in SHADER_READ_ONLY_OPTIMAL. This matches how D3D12 already needs ALLOW_UNORDERED_ACCESS, adds no decision for the user, and keeps P16. Alternatively, the doc can choose "GENERAL for all non-attachment textures". Measurement item 3 (storage write -> sample) should explicitly cover the case of a texture resting in GENERAL on RDNA2 Vulkan without the extension.

### R10. GPU_UPLOAD on D3D12 is all-or-nothing (full ReBAR plus Windows 11), not a 'small window'

- Items: P32  ·  Kind: factual-error  ·  Reviewer severity: medium
- Finding: P32 says: "systems without resizable BAR expose only a small window". That is true on Vulkan, where a DEVICE_LOCAL|HOST_VISIBLE heap of about 256 MB exists without ReBAR. It is false on D3D12. D3D12_HEAP_TYPE_GPU_UPLOAD is reported (OPTIONS16::GPUUploadHeapSupported) only when the entire VRAM is CPU-visible, meaning ReBAR is enabled in the BIOS on dGPUs. Otherwise it is not available at all. The retail feature (Agility 1.613+) also needs Windows 11 build 26080+ (24H2), and P2 only says "Windows". Sources: https://github.com/microsoft/DirectX-Specs/blob/master/d3d/D3D12GPUUploadHeaps.md , https://gpuopen.com/learn/using-d3d12-heap-type-gpu-upload/
- Suggestion: Reword P32. On Vulkan, the size of the GPU + CPU write kind varies (256 MB window without ReBAR). On D3D12 the kind is either fully present or absent: it needs ReBAR and Windows 11 24H2. The capability query should report availability as well as size, per backend.
- Verifier: Severity: low (a wording fix, no design change). Reword the text in brackets in P32 for each backend. On Vulkan, a system without ReBAR has only a small device-local + host-visible window (about 256 MB). On D3D12, GPU_UPLOAD is either all or nothing: it is reported only when all of VRAM is CPU-visible (ReBAR enabled), and it needs a recent Agility SDK and Windows 11 build. Otherwise the kind is absent. The capability query that reports availability and size already covers this.

### R14. 64-bit atomics on bindless (heap-indexed) resources need a separate D3D12 capability

- Items: Feature scope: 64-bit atomics, P30  ·  Kind: gap  ·  Reviewer severity: low
- Finding: The table says "Buffer atomics are SM 6.6 / VK_KHR_shader_atomic_int64. Image atomics are a separate optional capability." On D3D12, 64-bit atomics on a resource reached through ResourceDescriptorHeap (the bindless style in P30) are gated by D3D12_FEATURE_DATA_D3D12_OPTIONS11::AtomicInt64OnDescriptorHeapResourceSupported. This is separate from SM 6.6 and from AtomicInt64OnTypedResourceSupported (textures and typed buffers). On Vulkan, image int64 atomics are VK_EXT_shader_image_atomic_int64.
- Suggestion: List the three D3D12 caps (Int64ShaderOps / AtomicInt64OnTypedResourceSupported / AtomicInt64OnDescriptorHeapResourceSupported) and VK_EXT_shader_image_atomic_int64 as the capability-query inputs.
- Verifier: Mostly correct, with one change to the suggested list. Int64ShaderOps (OPTIONS1) covers general int64 shader arithmetic, not atomics specifically, so it is a prerequisite rather than an atomics cap. The D3D12 atomic caps to list are OPTIONS9::AtomicInt64OnTypedResourceSupported, OPTIONS9::AtomicInt64OnGroupSharedSupported and OPTIONS11::AtomicInt64OnDescriptorHeapResourceSupported (the one that matters for P30's heap-indexed style), on top of SM 6.6. On Vulkan, buffer and shared-memory atomics come from VK_KHR_shader_atomic_int64 (core in 1.2, but its feature bits still need checking) and image atomics from VK_EXT_shader_image_atomic_int64. Turing and RDNA2 likely expose all of these, so this is a one-line fix to the note and capability query, not a design change.

### R15. Level-1 multi-draw indirect: D3D12 shaders cannot tell which draw they belong to

- Items: P48  ·  Kind: gap  ·  Reviewer severity: low
- Finding: P48 Level 1 offers "GPU-written arguments and draw counts for indexed draws" on both backends. Vulkan shaders can read the draw index (DXC [[vk::builtin("DrawIndex")]] -> gl_DrawID). HLSL/DXIL has no draw-ID system value: SM 6.8 adds only SV_StartVertexLocation and SV_StartInstanceLocation. On D3D12, the usual way to identify the draw is an ExecuteIndirect root constant per draw, which P48 classifies as Level 2 "behind a capability query". On D3D12 that form is core and always available: changing root constants is supported on all ExecuteIndirect tiers. So Level 1 is less capable on D3D12 than on Vulkan, and Level 2 is never actually optional there.
- Suggestion: Note in P48 that D3D12 has no draw-ID builtin. The portable per-draw identifier is a Level-2 root constant (always present on D3D12, DGC-gated on Vulkan), or a firstInstance/StartInstanceLocation trick in Level 1.
- Verifier: One point needs softening. Putting Level 2 "behind a capability query" is not wrong. On D3D12 the query simply always returns true, so P11 still holds. The real gap is that Level 1 has no portable per-draw identifier. On Vulkan, DrawIndex works. On D3D12 the options are a Level-2 root constant, which is always available there, or a firstInstance trick. Note that D3D12's SV_InstanceID does not include StartInstanceLocation, so that trick needs SM 6.8 SV_StartInstanceLocation or an instance-rate vertex attribute. Separately, CONTEXT.md line 99 still says "The level is open" for indirect execution, even though P48 settled it. That is a stale line worth fixing in the same edit.

### R16. Unified layouts still need initial and discard transitions, not just present

- Items: LayoutEvaluation.md, L1, P35  ·  Kind: ambiguity  ·  Reviewer severity: low
- Finding: LayoutEvaluation says that with VK_KHR_unified_image_layouts, "The single layout change is swapchain GENERAL → PRESENT_SRC at present". Images are still created in UNDEFINED and need a one-time UNDEFINED -> GENERAL transition. Aliased or discarded images (the P35 discard command) need UNDEFINED -> GENERAL again to drop their contents. Swapchain images also go PRESENT_SRC -> GENERAL after acquire. The extension only promises that GENERAL is as fast as the optimal layouts; it does not remove those image barriers. The driver-coverage facts are correct: NVIDIA 573.38 / 570.123.18 on 2025-06-08, and RADV RDNA3+ only in Mesa 25.2.
- Suggestion: List the remaining per-image transitions: initial, discard/alias, and acquire/present. A' then names an image in exactly those base-owned operations.
- Verifier: Rewrite the Vulkan + unified-layouts row to say that every image rests in GENERAL and that user barriers are only VkMemoryBarrier2. The only remaining layout transitions should be listed as base-owned and naming one image each: (a) UNDEFINED → GENERAL, once at texture creation or first use; (b) UNDEFINED → GENERAL on the P35 discard or aliasing command; (c) swapchain acquire → GENERAL (from UNDEFINED when the contents are discarded, as in the running example, otherwise from PRESENT_SRC); and (d) GENERAL → PRESENT_SRC at present. The same base-owned initial and discard transitions also apply on D3D12 (into DIRECT_QUEUE_COMMON) and on Vulkan without the extension.

### R50. Acceleration-structure compaction lacks the compacted-size query

- Items: P49, P47, P51  ·  Kind: gap  ·  Reviewer severity: low
- Finding: P49 gives a prebuild size query and a `compact` command. Compaction needs the compacted size, which only the GPU produces after the build: D3D12 EmitRaytracingAccelerationStructurePostbuildInfo, or Vulkan vkCmdWriteAccelerationStructuresPropertiesKHR into a COMPACTED_SIZE query pool. The user must then read it back and allocate the destination. Without this, user-placed compaction (the level-2 control form under P41) cannot be written.
- Suggestion: Add a recorded 'emit compacted size' command that writes into a user buffer (or a query pool under P51), and document the readback-then-place sequence.
- Verifier: Severity stays low. The most consistent fix is to add a "compacted size" query type to the P51 query pools and record it with a command such as `writeAccelerationStructureCompactedSize`, then resolve it through `resolveQueries`. This matches Vulkan's model directly. On D3D12, the same thing can be built by emitting the postbuild info into a buffer.

Under the current layout direction A' (LayoutEvaluation.md, lines 43 and 137-138), the base already has to execute the swapchain's final layout change to the present layout itself. The other points are not decision-level gaps either. Whether submit takes several command lists, and whether present returns a timeline point, are API surface questions. U1 (the ideal hello-world, including texture → swapchain) is explicitly deferred, and the user leans toward raw-Vulkan-like code. - Shader hot reload and pipeline replacement are not addressed: The design notes never use the words "hot reload", "pipeline replacement" or "pipeline cache", but the hot-reload part of the finding is already answered by decisions on record:

- P20 gives timeline points, and makes deferred destruction a helper built on them.
- P41 says "Apply it by default to new topics": RI exposes the explicit form, and the automatic form is a helper built only on RI's public surface.

Together these settle hot reload with no new decision. RI does create and destroy. A reload helper compiles the new bytecode, creates the new pipeline, and retires the old one once its timeline point has passed. A helper can also give a stable identity by adding one level of indirection.
