# What vulkan_sandboxCailloux asks of RI (2026-10-15)

The user asked, before starting the layer above RI, which features of
`Raven33/vulkan_sandboxCailloux` belong in RI. Read: the sandbox at `main` (pushed
2026-10-13, all of `src/` and `shaders/`) and the renderer it runs on, `Raven33/EquineEngine`
at `86caf7e` (its submodule pin). Nothing was built or run.

The sandbox is a research app for mesh-shader rock piles (the RockPiles2 paper workload): GPU
seeding, compute passes chained by indirect dispatches, task/mesh rendering, a shadow atlas,
IBL, and a benchmark runner that writes CSV files.

Each finding goes in one of three places:

- **RI core**: RI cannot do it today, or reports too little. These need the user's approval
  (signatures change).
- **RI helper**: RI can do it, but every project would write the same code. Helpers first,
  promoted later if the user wants.
- **The layer above**: opinions about how a frame or an app is organised (P35, P80).

## Decisions (user, 2026-10-15; P105)

- 1.1 rendering without attachments: **yes**, in core.
- 1.2 mesh and task counters: **yes**, in core.
- 1.3 64-bit atomics: **yes**: a `DeviceLimits` field, plus a validation check at pipeline
  creation (RI's own reflection, so both backends give the same message).
- Blit: **no** core command. Mip generation becomes a high-performance downsampler helper.
- The other helpers (section 2) and the thread question: later.

## 1. RI core

### 1.1 Rendering without attachments

The shadow atlas (`ShadowMapManager.hpp`) rasterizes with no attachments: viewport and
scissor select a tile, and the pixel shader writes depth with `imageAtomicMin` into an R32UI
storage texture. The engine allows this with `disableRenderTarget`, `disableDepthTarget`, and
`setRenderArea(w, h)`.

RI refuses it: `cmdBeginRendering` reports "a rendering section needs an attachment"
(`backends/vulkan/Commands.cpp:410`), and `RenderingDesc` has no size to use when there is no
attachment. Both APIs support it: Vulkan dynamic rendering takes `renderArea` and
`layerCount` with zero attachments; D3D12 takes `OMSetRenderTargets(0, …)` and a viewport.
The D3D12 backend already handles empty colors.

Today's workaround is a dummy color target, which costs memory and bandwidth for nothing.

Possible shape (to discuss): an optional size in `RenderingDesc`, required when there is no
attachment and checked against attachments when there are some.

```cpp
struct RenderingDesc {
    std::vector<ColorAttachment> colors;
    std::optional<DepthAttachment> depth;
    std::optional<RenderArea> area; // new: width, height, layers; required with no attachment
};
```

### 1.2 Mesh and task counters in pipeline statistics

The benchmarks record `MeshPrimitiveCount` for each parameter combination
(`SubAppRockPiles2.hpp`, `recordFrameMetrics`). The engine gets it from Vulkan's mesh-shader
query.

`PipelineStatisticsLayout` (`src/RI/Textures.hpp:330`) and the helper's
`PipelineStatistics` have no task or mesh counters. The APIs have them:

- Vulkan (`VK_EXT_mesh_shader`): statistics bits `TASK_SHADER_INVOCATIONS_BIT_EXT` and
  `MESH_SHADER_INVOCATIONS_BIT_EXT`; primitives are a separate query type,
  `VK_QUERY_TYPE_MESH_PRIMITIVES_GENERATED_EXT`.
- D3D12: `D3D12_QUERY_TYPE_PIPELINE_STATISTICS1` (`ASInvocations`, `MSInvocations`,
  `MSPrimitives`), behind `OPTIONS9::MeshShaderPipelineStatsSupported`.

Possible shape: three more offsets in `PipelineStatisticsLayout` (`kNoCounter` when
unsupported, as P102 does for other stages) and three fields in the helper struct. The
Vulkan primitive count is a different query type, so RI would issue it alongside the
statistics query or add a query kind. That choice needs a decision.

### 1.3 A capability flag for 64-bit atomics

The JFA pass of RockPiles2 uses `GL_EXT_shader_atomic_int64` (`uint64_t` atomics on
buffers). CONTEXT §2 lists 64-bit atomics as "In" with their capability inputs, but
`DeviceLimits` has no flag, and neither backend queries them. The D3D12 backend never reads
`OPTIONS9` or `OPTIONS11`. On Vulkan they work because RI turns on every supported feature
(P60), but code cannot ask RI whether they are there.

Possible shape: `DeviceLimits::int64Atomics` (buffers and shared memory, heap-indexed on
D3D12), plus `int64ImageAtomics` if a workload needs it (the sandbox does not: its image
atomics are 32-bit).

### Covered already

Checked against the sandbox's use, with no change needed:

- indirect dispatch and indirect mesh draws (P48 level 1)
- mesh shaders
- buffer and texture clears (P65; the sandbox's `ClearBufferUtil` is a compute shader for
  this)
- timestamps
- 32-bit image atomics
- viewport and scissor (P103)
- present modes
- the subgroup operations the shaders use (HLSL wave operations; on Vulkan, subgroup
  support is core)

## 2. RI helpers

### 2.1 Readback and upload rings (strongest case)

RockPiles2 reads its allocator state back **every frame** (`postRender` →
`downloadFromBuffer`). In the engine each call creates a staging buffer, submits, waits on a
fence, and frees the buffer (`VulkanRendererUtils.cpp:203`, `endSingleTimeCommands`). So the
CPU waits for the GPU once per frame. This may be part of the frame-pacing problem the
shadow manager's TODO describes, but that was not measured.

RI's `Transfers` helper has the same shape: it waits, by design, and is meant for loading.
What is missing is a ring tied to `FrameRing`. Each frame records a copy into its own slot of
readback memory, and the CPU reads that slot once the frame's timeline point is reached, N
frames later, without waiting. The upload side is the same idea in reverse: a linear
per-frame allocator in upload memory for the constants and small data the CPU writes each
frame. In the engine, managed UBOs did this for you.

### 2.2 Mip generation

`generateMipMaps` is called 6 times (PBR materials, ARMS textures). RI has no blit, since
D3D12 has none, so a helper needs a compute downsample with its own pipeline. sRGB textures
need a UNORM view format to be written as storage (P74 `viewFormats`). The helper should say
so, or check it.

### 2.3 ImGui renderer

The sandbox's whole UI is ImGui, and the engine built it in (`VulkanRendererImGUI.cpp`,
`getImGuiCompatibleTextureHandle`). An RI version would serve both backends with one code
path: vertices pulled from a buffer (P39), textures as heap slots (`ImTextureID` = slot),
and the projection in root data. Like the GLFW helper, it would sit in its own library
because it depends on a third-party project.

### 2.4 Shader hot reload

The sandbox has a "Reload Shaders" button, and the engine rehashes the source. On RI this
needs three things:

1. `compileShader` reports the files it included, so a watcher knows what to check. DXC
   gives this through the include handler.
2. The pipeline is recreated.
3. The old pipeline is destroyed after its last use (a timeline point, like the
   allocators' deferred frees).

Only the first touches an existing helper: `CompiledShader` would grow a list of
dependencies.

### 2.5 Smaller ones

- **Submit and wait.** The SDF build runs once per model load (`ExecutionPolicy::Standalone`).
  `Transfers` already does "make a list, submit, wait" inside; exposing it as one call saves
  every project from writing it.
- **CPU scopes in the profiler.** The sandbox profiler puts CPU and GPU zones in one tree.
  RI's profiler only has GPU scopes. CPU scopes would be a small addition; the UI that shows
  the tree belongs above.

### A question that touches core: threads

The sandbox builds its pipelines in parallel (`initPipelinesParallel`, `std::async`). RI is
single-threaded by design (P56; `concepts/timeline.md`: "RI objects are not thread-safe").
Both native APIs allow pipeline creation from several threads, and shader compilation is
usually the slow part. Two separate questions:

1. May each thread use its own `ShaderCompiler`? Probably yes; it needs checking and
   documenting.
2. Should `createComputePipeline`/`createGraphicsPipeline` be callable from several threads?
   That would change P56 for creation only (not recording). It is the user's decision.

## 3. The layer above (EquineEngine V3)

These are opinions about how an app or a frame works, so they stay out of RI (P35, P80).
Listed so the layer above can start from them.

**Research tooling.** This is the most valuable part of the sandbox, and it does not depend
on any GPU API:

- `ParameterCombinator`: linear or log steps, read from a CSV config.
- `Benchmarker`: collects frames until the 95% confidence interval is within a threshold,
  with min and max frame counts. Writes mean, standard deviation, and variance per metric to
  CSV.
- A one-minute GPU warm-up.
- Power draw through NVML (Windows and NVIDIA only).

Lesson from P96 to carry over: integrated GPUs change clock states, and only runs that
interleave the variants control for it. The sandbox runs each combination in a block.
`tools/layout_bench` interleaves frame by frame.

**App shell:**

- a sub-app registry, switchable at run time
- an ImGui menu bar
- no-sync, vsync, or a target frame rate (sleep)
- a fullscreen toggle
- finding the project root

**Rendering pieces:**

- fly camera and debug camera with frustum display
- lights and a light manager that hands out shadow tiles
- shadow atlas
- IBL precompute (equirect to cube, irradiance, prefilter, BRDF LUT)
- PBR material loading (stb images loaded in parallel, AO/roughness/specular packed into one
  texture)
- OBJ and glTF loaders (skeletons, animations)
- icosphere and dual generators
- a GPU-to-OBJ exporter
- the `DevHelper` tweak block

The IBL code packs cube faces and mips into 2D atlases because the engine lacked cube and
per-mip views. On RI (P102) it can use real cube textures.

**What the engine did for you that RI leaves to the layer above, on purpose:**

- uniform blocks bound by name through reflection
- automatic barriers and layout tracking on `useResource` (P36)
- command lists cached by hash
- per-frame copies of textures, and "previous frame's depth"
- a default swapchain depth target
- deferred deletion inside the renderer

A frame graph above RI (P35) is where most of these get decided.

**Shaders.** The sandbox's shaders are GLSL:

- 61 files (shaders and includes)
- `GL_EXT_mesh_shader`, scalar block layout, subgroup ballot, vote, shuffle, and arithmetic
- 64-bit atomics

RI takes HLSL through its compile rule (P93, P94). Moving this code onto RI means rewriting
the shaders in HLSL. That is not an RI feature, but it is the largest single cost of a port.
