## 2. Two decisions for the user

**Decided (user, 2026-11-12).** (a) Bindful constant buffers stay unsupported on Metal, behind
`DeviceLimits::constantBuffers` (on `p112-constant-buffers`; P116 (6) on `metal-backend`).
(b) Option 1: `SV_VertexID` leaves out the first vertex and the vertex offset everywhere (P117,
on master, with the test `texture.vertex_id_excludes_offsets`; it failed on RADV before the
change, which confirms Vulkan's side; D3D12 and Metal are still to run). The text below is the
question as it was asked.

**(a) Bindful constant buffers on Metal.** P114 (1) gives every Metal shader one fixed root
signature of 64 root constants: the whole 64-DWORD root budget. P112 (3) puts root CBVs in that
budget (8 bytes per slot), and the Metal backend refuses any declared resource
(`reflectStage`, `backends/metal/Pipeline.cpp`). So P112 cannot exist on Metal as both stand.
Options: fewer root constants in the fixed signature (lowers `maxRootDataSize` on Metal: 192
bytes leaves room for 8 slots); a root signature per shader (MSC run with a signature built
from the DXIL, so the top-level argument buffer's layout varies per pipeline); or P112
unsupported on Metal behind a `DeviceLimits` flag.

**(b) What `SV_VertexID` holds.** Master promises, in `docs/site/docs/reference/cmdDraw.md` and
in both `Backend.hpp`, that `SV_VertexID` runs from `firstVertex` and that indexed draws give
the index plus `vertexOffset`. That is Vulkan's rule (`gl_VertexIndex`). To my knowledge D3D12
adds neither (which is why SM 6.8 has `SV_StartVertexLocation`), and Metal Shader Converter
subtracts the base vertex to match D3D12. The Metal `Backend.hpp` says the opposite of D3D12
("D3D12 adds vertexOffset"). No test on any backend draws with a first vertex or vertex offset
other than 0 (every `cmdDraw` and `cmdDrawIndexed` in `tests/` leaves them at 0), so nothing
has shown which is true. With vertex pulling (P39) this is the value users index their buffers
with. First step: one portable test with `firstVertex` and `vertexOffset` set, run on all three
backends. Then the user picks the contract (index alone everywhere, with the offset passed in
root data; or the offset added everywhere, which needs shader-side work on D3D12 and Metal).

## 3. Metal backend

No crash was found by reading. In order of weight:

1. **Command memory only grows.** `allocateCommandMemory` (`Commands.cpp`) makes each new chunk
   twice the last and keeps every chunk until the list is destroyed. Texture copies between
   different pixel formats, and every copy of a format with stencil, stage the whole image
   through it (`copyThroughBuffer`, `TextureCommands.cpp`). One 4K depth-stencil copy takes
   about 33 MB that never comes back, and the next chunk is twice that. Fix: a size cap on
   doubling, and chunks above it released at reset.
2. **Staged copies of multisampled textures.** `needsStaging` sends multisampled depth-stencil
   copies, and multisampled copies between formats, through a buffer; Metal copies no
   multisampled texture to a buffer. `checkCopyTextureMatch` lets them through. The handoff
   lists copies between formats as untested. Fix: report them, or resolve the rule on every
   backend.
3. **GPU-written indirect counts are not measured (P18).** With a count, RI copies every record
   and encodes `maxCount` draws on the CPU (`Indirect.cpp`). P116 (3) says an ICB is measured
   against it "later"; the path shipped first.
4. **`acquire` never gives up.** It loops on `nextDrawable` (`Swapchain.cpp`), which returns
   nil each second while no drawable comes (display asleep). It runs on the thread that owns
   the window, so the event loop stops with it. D3D12 and Vulkan return.
5. **64 KiB per acceleration structure.** `accelerationStructureRequirements`
   (`RayTracing.cpp`) aligns and rounds every structure to `kHeapGranularity`, and bottom
   levels also pay for the top level's header (the query does not know the kind). A scene of
   10,000 small bottom levels takes at least 640 MB. Metal's own alignment is what
   `heapAccelerationStructureSizeAndAlign` returns.
6. **The format table was checked on the M4 only.** `formatSupported` (`Textures.cpp`) is a
   table; its header says Metal reports no format capability at run time, but
   `supports32BitMSAA` and `supports32BitFloatFiltering` exist and are not read. On M1 and M2,
   the 32-bit float formats and `rayTracingHardware` are unverified.
7. **The Metal test list is a copy by hand** (`tests/CMakeLists.txt`). It has no
   `registry_matches` entry, and cannot have one as is: the executable compiles cases it does
   not register (`texture.occlusion_and_statistics`, `texture.mesh_statistics`,
   `helpers.shader_compiler`). A case added to the shared list does not run on Metal unless
   someone adds it there too. Fix: build the Metal list from the shared one minus a named
   skip list, and compile the three cases out on Metal.
8. **Smaller:**
   - `cmdBuildBlas` accepts a structure created as a top level (`cmdBuildTlas` checks the
     reverse). No backend checks it; the rule belongs in `src/RI/Validation`.
   - A scissor wholly outside the section is clipped to a width or height of 0
     (`applyScissor`, `Rendering.cpp`); Metal may refuse it.
   - HDR10 sets the PQ color space but no EDR metadata, and was never seen on a screen.
   - The path from a GPU error to `eDeviceLost` has no test (the handoff says so too).
   - `checkViewUsage` and `checkTextureViewUsage` live in `Resources.cpp`, not in
     `src/RI/Validation`, so D3D12 and Vulkan do not have them.
   - Sampling a read-only depth attachment inside its section is untested on Metal.
9. **Toolchain.** Everything rests on Metal Shader Converter 4.0 beta 3 (behind an Apple ID,
   crashes on the string form of flags, its manual wrong on sampler entries), a DXC built by
   hand, and one borrowed M4. No CI can build it. Shaders cannot be compiled at run time on
   Metal (the helper gives plain DXIL), so no hot reload there.
10. **Documentation.** `ARCHITECTURE.md` still describes two backends (the branch changes 3
    lines): layout, call flow, invariants ("both backends, same signatures") and §5 need a
    Metal column. `HANDOFF.md` is untouched on the branch. Only four site pages mention Metal.

## 4. Outside Metal

1. **`d3d12.compute.write_small_data` fails on the AMD iGPU with the Agility SDK preview**
   (1.715.1), in both runs: `2e15e22` and `a5dfa79`
   (`docs/measurements/windows/verify/*/clangcl-debug-preview_ctest_amd.log` on
   `win-verify-p110-p112`; wrong values at `ComputeTests.cpp:404`, `406`, `408`). It passes with
   the retail SDK and on NVIDIA. No document mentions it. Master's handoff asked Windows to
   check that `WriteBufferImmediate` is synchronized by `Stage::eCopy`: either that is the bug,
   or the preview runtime is. P111 depends on the preview.
2. **D3D12 UAV clears share 1024 descriptors with no guard** (`clearNext`,
   `backends/d3d12/Rendering.cpp`; `kClearHeapSize`). Each texture clear and each piece of a
   buffer clear takes the next slot of a ring in a shader-visible heap. After 1024 clears not
   yet executed, a slot is written again while a recorded clear still names it. Fix: count the
   slots taken since the last completed submission and report (or wait) at 1024.
3. **Master has the wrong shader-kind numbers** in `src/RI/Reflection/Dxil.cpp`
   (`kPsvStageAmplification` 8, `kPsvStageMesh` 9; they are 14 and 13). Nothing on master reads
   them. The fix is on `metal-backend` only.
4. **P111:** the input limits are behind a compile-time macro with no `DeviceLimits` flag, so a
   program cannot ask at run time; and a dispatch past the promise is checked in validation
   builds only.
5. **P112:** `docs/measurements/constant_buffers/README.md` says NVIDIA and AMD Windows are not
   measured. They are: the CSV files are on `win-verify-p110-p112`, unmerged, and nobody has
   written what they show (on the RTX 3080, recording a push costs about 185 ns against 169 for
   a heap index, and GPU times are equal).

6. **The docs generator stopped on `metal-backend`** (`KeyError: 'metal'` in
   `docs/site/scripts/extract_headers.py`), so the docs CI job could not pass there. Fixed on
   that branch (2026-11-12); the strict `mkdocs` build was not run.
